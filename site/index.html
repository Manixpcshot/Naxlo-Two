Two ways to decide which node to use

The ranking is the product. Most clients sort by “last ping won”, which is how a node that answers 40 ms once and drops every third connection ends up on top. Naxlo Two keeps a model per node instead, and publishes how it is computed so you can argue with it.

Simple mode

Latency and recent success rate, nothing else. Predictable, and the right choice when you want the switch decision to be obvious to a second reader.

Advanced mode

An EWMA over latency with a half-life, so an old sample fades instead of being overwritten; jitter, reliability and throughput as separate terms; and Thompson sampling, which keeps exploring a node that has been quiet rather than condemning it forever.

Weights you can move

Latency, jitter, reliability, throughput, freshness, stability and stickiness are seven sliders. Presets for “speed first” and “steady first” are starting points, not verdicts.

It refuses to flap

A switch needs a real margin plus a dwell time, the margin doubles after recent flips, and a node you pinned is never moved. “Something is 4 ms faster” is not a reason to rebuild your tunnel.

Updates, read from GitHub itself

The app asks GitHub’s Releases API — the same endpoint the website uses — for the newest published release, picks the asset for its platform, and shows you the version, the size, the exact URL and the full digest. “Download” fetches it into a temp directory; “Install & restart” only appears once the bytes on disk hash to what the release says they hash to. A release published without a digest can be announced but never run.

The repo’s release manifest is read alongside it for the parts GitHub cannot express: a block list of known-bad versions and the ratchet that says “anything older than this must move”. The two are merged per platform — GitHub for what exists, the manifest for what is allowed — and the settings screen tells you which one answered, because “up to date” from a dead endpoint is not the same sentence.

Privacy is a build-time fact, not a promise

The app talks to three kinds of place: the servers you added, the subscription URL you pasted, and GitHub for updates. That list is enforced in CI by grepping the source for analytics SDK imports, tracking hosts and device-identifier generation — so a future commit cannot add telemetry quietly.

No accounts, no phone-home

No crash reporter, no analytics, no “anonymous usage statistics”. Nothing is sent when you install, open or close the app.

Your config stays on disk

Profiles, nodes and measurements are written to your own config directory as plain JSON you can read, diff and copy to another machine.

Probes stay probes

Latency probes open a TLS handshake to your own node with an SNI you can set. They carry no payload and never touch a third-party endpoint.

Built for you to read

Flutter and Dart on top of the Xray-core engine (sing-box as an alternate engine for the routing paths where it fits better). No fork of anyone’s client: the UI, the ranking, the packaging and the release pipeline are written here, in the open, and every merge to main bumps the version, tags it, builds installers and publishes the release — including the update manifest the app reads.

  • Engines — Xray-core v26.10.21, sing-box v1.14.4, pinned by digest in engine-lock.json and fetched with checksum verification.
  • Protocols — VLESS (Reality), VMess, Trojan, Shadowsocks, SOCKS; TCP, WebSocket, gRPC, h2 and xhttp transports.
  • CI — six checks per pull request, and the generated configs are fed to the real xray / sing-box binaries so an invented JSON key cannot ship.
